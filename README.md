# qa-demo-arctf

Демонстрационный проект для портфолио: тестовый фреймворк для UI и API автоматизации формы регистрации и авторизации. Тестируемое приложение (SUT) - упрощенная песочница в стилистике arctf.online. Основной артефакт репозитория - автотесты, моки внешних сервисов и QA-документация.

Проект демонстрирует подход к автоматизации, примененный при тестировании внутренних систем АГУ (сайты мероприятий, хакатонов, системы контроля посещаемости).

## Что внутри

- API-тесты регистрации и авторизации (позитивные, негативные, граничные значения, валидация JSON-схем)
- UI E2E-тесты полного пользовательского сценария (регистрация - вход - проверка профиля)
- Unit-тесты с моками внешних зависимостей
- Page Object Model для UI-тестов
- Параллельный запуск через pytest-xdist
- Allure Report с вложениями (скриншоты, логи запросов)
- Тестовая документация (тест-план, примеры баг-репортов, чек-листы с применением Pairwise)

## Структура

```

  - bug_report_BR-XXX.md # пример критического дефекта перед релизом

## Как запустить

### 1. Поднять тестируемое приложение

```bash
cd app
docker-compose up -d --build
```

Приложение будет доступно на http://localhost:8000

### 2. Установить зависимости для тестов

```bash
cd app
pip install -r requirements.txt
cd ..
cd tests
pip install -r requirements.txt
```

### 3. Запустить тесты

Все тесты:
```bash
pytest tests/ --alluredir=allure-results
```

Только API-тесты:
```bash
pytest tests/api/ -v
```

Только UI-тесты:
```bash
pytest tests/ui/ -v
```

Параллельный запуск (4 потока):
```bash
pytest tests/ -n 4 --alluredir=allure-results
```

### 4. Сгенерировать Allure-отчет

```bash
allure generate allure-results -o allure-report --clean
allure open allure-report
```

## Тестовая документация

В папке `docs/` лежат примеры артефактов, которые использовались в реальной работе:

- `test_plan.md` - тест-план с приоритизацией по рискам (что тестируем в первую очередь при сжатых сроках)
- `bug_report_example.md` - пример оформления критического дефекта, обнаруженного за день до релиза
- `pairwise_checklist.md` - чек-лист с применением техники попарного тестирования (сокращение количества сценариев на 30%)
- `manual_test_checklist.md` - чек-лист ручного тестирования- позитивные, негативные сценарии, граничные значения и тд

## Unit-тестирование и стратегия мокирования
Помимо интеграционных E2E-тестов, в проекте реализован слой изолированных unit-тестов (tests/unit/). Этот подход критически важен для быстрой обратной связи и стабильности CI/CD.
Ключевые практики, примененные в проекте:

    Изоляция внешних зависимостей: Использование pytest-mock для подмены реальных вызовов (например, отправка email или запросы к сторонним API) на контролируемые заглушки. Это исключает сетевые задержки и делает тесты детерминированными.
    Testable Code Design: Решение проблемы мокинга встроенных функций в Python 3.11+ (например, datetime.utcnow) путем выноса логики в отдельные функции-обертки, что позволяет легко патчить поведение без изменения бизнес-логики.
    Тестирование бизнес-логики без БД: Использование фиктивных объектов (Mock objects) для эмуляции поведения курсора базы данных, что позволяет проверять ветвления (if/else) за миллисекунды, не поднимая тестовое окружение БД.
Запуск unit-тестов:
```bash
# Перейти в папку tests
cd tests

# Запустить все тесты разом (API + UI + Unit)
pytest api/ ui/ unit/ -v --alluredir=allure-results

# Сгенерировать отчет
allure generate allure-results -o allure-report --clean

allure open allure-report
